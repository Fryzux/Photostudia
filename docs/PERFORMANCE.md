# Оптимизация производительности: кэширование и предрасчёт

## Что сделано

### Бэкенд
| Изменение | Файлы |
|---|---|
| Кэш ответов в Redis (`CACHE_REDIS_URL`, БД Redis `/1`, отдельно от брокера Celery на `/0`) | `core/settings.py`, `docker-compose*.yml` |
| Инвалидация через версии пространств имён: сигнал `post_save`/`post_delete` делает один `INCR` версии, старые ключи становятся недостижимы и истекают по TTL. Сброс выполняется в `transaction.on_commit`, чтобы откат транзакции не испортил кэш | `studio/cache.py`, `studio/signals.py`, `studio/apps.py` |
| Кэшируются: список/карточка зала (1 ч), услуги (1 ч), свободные слоты (5 мин), сводная аналитика (2 мин), AI-прогнозы (1 ч) | `studio/views.py`, `ai/views.py` |
| AI: недельный прогноз и прогноз за период считаются **одним** вызовом `predict_proba` вместо вызова на каждый день | `ai/services.py`, `ai/views.py` |
| `GET /api/orders/`: устранён N+1 (`prefetch_related('booking__hall__gallery_images')`) — 22 SQL-запроса → 3 | `studio/views.py` |
| Аналитика: число заказов и выручка — одним `aggregate` | `studio/views.py` |
| Индексы: `Booking(hall, start_time)`, `Order(user, -created_at)`, `Order(-created_at)`, `Order(status)` | `studio/models.py`, `studio/migrations/0010_perf_indexes.py` |
| HTTP-кэш: `Cache-Control` для залов и услуг, `ETag` + `304 Not Modified` (`ConditionalGetMiddleware`) | `core/settings.py`, `studio/views.py` |
| Попутно исправлено: свободные слоты не учитывали бронь, начавшуюся накануне и заканчивающуюся в этот день | `studio/views.py` |

Ключи, в которых есть данные пользователя (аналитика), всегда содержат `user_id`; ответы для персонала и для остальных кэшируются под разными ключами.

### Фронтенд
| Изменение | Файлы |
|---|---|
| `@tanstack/react-query`: общий кэш запросов между страницами. Залы и услуги свежие 5 мин, слоты — 10 с с фоновым опросом раз в 15 с | `src/app/hooks/queries.ts`, `src/app/App.tsx` |

## Методика замеров

**API** — `perf/bench_api.py`, запуск внутри контейнера backend (настоящие PostgreSQL 15 и Redis):

```bash
docker exec -e CACHE_REDIS_URL=redis://redis:6379/2 -e BENCH_OUT=/app/docs/perf/after.json \
  photostudia_backend python manage.py test perf.bench_api --noinput
```

- Отдельная временная тестовая БД, рабочие данные не затрагиваются.
- Данные: 6 залов, 18 фото, 8 услуг, 200 пользователей, 3000 броней с заказами.
- Каждый эндпоинт вызывается 30 раз подряд. **Первый запрос** — пустой кэш; **медиана / p95** — запросы 2–30; SQL — число запросов к БД.
- Время измеряется внутри процесса (без сети), т.е. это время работы Django.

**Фронтенд** — старая (HEAD) и новая сборки, одинаковый сценарий навигации без перезагрузки страницы, считаются запросы к `/api/` через Resource Timing API. Детали — `docs/perf/frontend.json`.

Сырые данные: `docs/perf/baseline.json` (до), `docs/perf/after.json` (после).

## Ограничения

- `total_users` в админской аналитике не сбрасывается при регистрации — обновляется по TTL (2 мин).
- После переобучения модели (`train_hourly_model`) кэш прогнозов сбрасывается, но уже запущенный процесс держит старую модель в памяти до перезапуска (так было и раньше).
- В обычных тестах используется `DummyCache`, чтобы кэш не переносил данные между тестами; тесты кэша включают его явно (`studio.tests.ResponseCacheTests`).
